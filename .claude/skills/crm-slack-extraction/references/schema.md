# RCM Cooperative CRM Schema (Baserow)

Five tables, rebuilt against the actual live Baserow structure (confirmed via the read-only field-definitions API export, Sept 2026 — not a plan or a guess). Column names below are exact — copy them verbatim into the output CSV. Do not rename, reorder, or invent columns.

**Source material**: `docs/baserow-structure/` at the repo root holds the underlying reference material this schema and `scripts/build_workbook.py` were built from — kept there for audit/reference, not read by this skill at runtime:
- `baserow-structure-json-<Table>.json` — the raw field-definitions API export per table (formula text, select options, field types). This is what column names, types, select options and formulas above are confirmed from.

**Column order — deliberately NOT tracked.** An earlier version of this skill tried to make `build_workbook.py`'s output columns match Baserow's live on-screen order exactly, confirmed by manually screenshotting each table's "Hide columns" panel. That's been dropped: keeping a screenshot-derived order in sync with the live tables wasn't robust (it silently went stale whenever a column was reordered or added), and hardcoding one fixed order made it harder for anyone templating their own Baserow instance from RCM's to freely reorder their own columns. `build_workbook.py` now lays out each sheet in `ALL_HEADERS` order (i.e. the order columns are listed in this document/that script) and leaves formula/system columns out of the sheet entirely, since there's no more positional reason to reserve blank columns for them. Every generated workbook includes a "READ FIRST" sheet warning that columns must be matched by **header name**, not position, when copy-pasting into Baserow — see the note in `scripts/build_workbook.py`'s module docstring for the full explanation. Baserow's own Import feature can match by header name automatically; using it is scoped as a future development opportunity, not implemented here.

**Formula syntax note**: every formula on this platform uses Baserow's own syntax — `field('Column Name')` (single quotes, function call, not curly braces) and `concat(...)`/`isblank(...)` for string joining and blank-checks. This is different from the SeaTable syntax this schema used before the platform migration.

## People

`name-person` (formula), `name-person-first`, `name-person-last`, `email-1`, `email-2`, `email-3`, `carrer-current-role-title`, `organisations`, `communities-contributor-profile`, `communities-lead`, `communities-participant`, `interactions-lead`, `interactions-participant`, `pronouns`, `notes`, `github`, `institutional-profile`, `linkedin`, `ORCID`, `projects-contact`, `projects-lead`, `projects-contributors`, `career-stage`, `mapping-consent`, `Last modified`, `Last modified by`, `Created on`, `Created by`, `edit-row-link`

Notes:
- `name-person` is now an **auto-computed formula column** on this platform (unlike the old SeaTable version, where it was manually entered): `field('name-person-first')+ " " + field('name-person-last')`. Never write to it directly — populate `name-person-first` and `name-person-last` instead.
- `carrer-current-role-title` — yes, that's the real spelling in the live base (typo: "carrer"). This replaced the old `position` field. Copy it exactly.
- `organisations` — a genuine **Link to table** field (Organisations), not free text. Unlike the old SeaTable version, this is not a duplicate to avoid — it's the real, only affiliation link now, and should be populated as a link when the organisation already/will exist as a row, not typed as plain text.
- `communities-contributor-profile` — **multiple select**, not a link field. Confirmed options: `communications`, `engagement`, `project-management`, `technical`, `strategy`. This captures general contributor-profile competency areas (per the RCM Skills and Competency Framework), gathered once per person — not scoped per individual community.
- `communities-lead` / `communities-participant` / `interactions-lead` / `interactions-participant` / `projects-contact` / `projects-lead` / `projects-contributors` — Link to table fields (Communities / Communities / Interactions / Interactions / Projects / Projects / Projects respectively). `communities-participant` is a genuinely separate field from `communities-lead` — added to the live base after this skill's schema knowledge was first written, confirmed via a fresh field-definitions export, Sept 2026.
- `pronouns` — **multiple select**. Confirmed options: `she/her`, `he/him`, `she/they`, `they/she`, `they/them`, `he/they`, `they/he`, `self identify`.
- `career-stage` — single select. Confirmed options (corrected against a fresh field-definitions export, Sept 2026 — the previous list documented here, `undergrad`/`grad-student`/`ecr`/`senior`/`pi`/`director`, did not match the live base at all): `Undergraduate student`, `Graduate Student`, `Early Career`, `Mid Career`, `Project Lead`, `Director`.
- `mapping-consent` — single select. Confirmed options: `consent-not-asked` (default), `consent-none`, `consent-internal`, `consent-public-pseudonymised`, `consent-public-identifiable`.
- `notes`: interest-area/background only — never what the meeting discussed.
- `email-3` — plain text, same pattern as `email-1`/`email-2`.
- `Last modified` / `Last modified by` / `Created on` / `Created by` / `edit-row-link` — Baserow system/read-only fields. Never write to these. `edit-row-link` is a read-only link to the self-nomination form's edit view (see the user-nominated fields note below); `Created on`/`Created by` are auto-tracked like `Last modified`/`Last modified by`. Note the capitalisation/spacing on `Last modified`/`Last modified by`/`Created on`/`Created by` doesn't match the `last-modified-by`/`last-modified-date` convention used on the other four tables — a naming inconsistency that's been flagged but not yet fixed.
- Only add a row for someone directly present at a meeting (attendee, or a named apology). See SKILL.md Step 1 for the one exception (quoted speakers when the attendee list is unreadable, which must be flagged/resolved with Cass first).

**`*-user-nominated` fields — not in this skill's writable column list, by design.** The live People table has seven additional fields tied to a self-nomination/signup form Cass built, where people submit information about themselves directly: `orgs-user-nominated`, `communities-lead-user-nominated`, `communities-participant-user-nominated`, `notes-user-nominated`, `pronouns-user-nominated`, `git-other-user-nominated`, `socials-other-user-nominated`. None of these are in `ALL_HEADERS` — a line targeting any of them fails validation as an unknown column, which is intentional, not an oversight.

The defining property of every `-user-nominated` field is **provenance, not topic**: it holds what a human typed about themselves through that form. A fact that happens to be topically similar — an organisation inferred from an email domain, a role inferred from a Slack message — is still machine-derived, not a person's self-report, and provenance decides write eligibility, not subject-matter overlap. No automated process should write to a `-user-nominated` field on the strength of "this looks like the kind of thing that goes here" — only an actual human-submitted-form value belongs there. With that principle set, the seven fields fall into two categories with opposite rules for any content-extraction skill (meeting notes, Slack activity, email threads):
  - **Staging inputs, never write to these**: `orgs-user-nominated`, `communities-lead-user-nominated`, `communities-participant-user-nominated`, `notes-user-nominated`. These hold exactly what a person typed into the self-nomination form; Cass manually reviews each one and decides whether/how to convert it into the real structured field (`organisations`, `communities-lead`, `communities-participant`, or folded into `notes`). If Slack activity ever states this kind of fact directly (e.g. a message stating "I lead the CSCCE community"), that's a candidate for the real `communities-lead` link field — subject to normal node-reconciliation — never for the `-user-nominated` staging field, even when the extracted value is confidently correct. The same logic would apply to any machine-derived organisation data this skill might one day produce (e.g. an organisation inferred purely from an email domain, not from anything a person stated about themselves): categorically different from a self-nomination however similar the resulting label looks, and never routed into `orgs-user-nominated`. **Does not currently apply to this skill in practice**: this skill has no email-domain-based (or any other) organisation-inference logic today — its only structured People facts are `name-person-first`/`name-person-last`/`email-1`, derived directly from Slack channel membership, so there is no machine-derived organisation candidate for this rule to guard against yet. Documented here as a guardrail for if that ever changes.
  - **Flexibility overflow, writable with a mandatory review flag — not currently used by this skill**: `pronouns-user-nominated`, `git-other-user-nominated`, `socials-other-user-nominated`. These exist to capture a real fact that doesn't fit a fixed field or picklist (non-standard pronouns, a non-GitHub git-hosting username, a non-LinkedIn social handle), always flagged for human review rather than accepted as settled. Category B is still bounded by the same provenance principle: what makes these writable is that the source itself is reporting a fact the person stated or displays (a pronoun line in an email signature, a handle in a Slack profile) — transcribing a stated fact into an overflow slot, not inventing or inferring one; the flexible format is not an invitation for a machine-derived guess to land here. **Does not currently apply to this skill in practice**: Slack export parsing (`parse_slack_export.py`) only reads channel membership (`real_name`, email), not Slack profile custom fields or message content, so this skill has no source for any of these three facts today and none are populated. If profile-field parsing is ever added, any such stated fact should route to these fields (with the flag), following the per-field formatting rules (verbatim text for pronouns; full URLs where possible for the other two; never write both `pronouns` and `pronouns-user-nominated` for the same fact).
  - `edit-row-link` is separately non-writable regardless of category — a read-only Baserow system field tied to the form view itself.
  - Rule of thumb: ask provenance first, then shape. A value that is not a genuine human self-report never goes into a `-user-nominated` field, full stop, regardless of topic match. Only once a value is confirmed as a genuine self-report does the second question apply — real link-field target elsewhere → forbidden, stays staged; scalar field the fixed picklist/format can't hold → writable, always flagged.

## Organisations

`name-org` (formula), `people-employees`, `type`, `name-org-long`, `name-org-abbreviation`, `notes`, `website`, `communities-sponsor`, `projects-sponsor`, `projects-funder`, `interactions-sponsor`, `interactions-funder`, `org-child-of`, `last-modified-by`, `last-modified-date`, `Created on`, `Created by`

Notes:
- `name-org` is an **auto-computed formula column**: `if(isblank(field('name-org-abbreviation')), field('name-org-long'), concat(field('name-org-long'), ' (', field('name-org-abbreviation'), ')'))`. Populate `name-org-long` (always) and `name-org-abbreviation` (only if given) instead; never write to `name-org` directly.
- `type` (single select, legal form — doesn't need to be precise, mainly for meaningful distinctions). **Exact picklist, use one of these only:**
  - `Academic institute` — a university or dedicated research body engaged in teaching and/or research.
  - `Consortium` — specifically an *academic* consortium: a formal grouping of multiple independent academic organisations collaborating on a shared initiative.
  - `Public sector / Government` — a national, regional, or local government body or agency.
  - `Private industry` — a for-profit commercial company.
  - `Non-profit` — an organisation not distributing profit to owners/shareholders, typically with charitable or public-benefit status.
  - `Funder` — an organisation whose primary role in the relationship is providing grant or programme funding.
  - `Intergovernmental organisation` — a body formed by and representing multiple national governments (e.g. UN agencies).
  - `Cooperative` — a member-owned organisation with democratic one-member-one-vote governance.
  - `Social enterprise` — a revenue-generating business whose profits are reinvested toward a social/environmental mission rather than distributed to shareholders.
  - If you cannot determine the type from the notes alone, leave blank and flag. Do not look it up online.
- `people-employees` — Link to People. This is the only People-link field on Organisations now (the old `people` vs `people-employees` split from an earlier draft has been resolved down to just this one).
- `communities-sponsor` / `projects-sponsor` / `projects-funder` / `interactions-sponsor` / `interactions-funder` — Link fields. Note Organisations can be linked to a Project or Interaction as *either* a sponsor *or* a funder (or both) — these are two distinct relationship types now, not a single combined `funder` field like the old SeaTable version. If the notes don't clearly distinguish sponsor vs funder, flag rather than guessing which one applies.
- Only add the **primary** organisation(s) actually under discussion — not every organisation mentioned in passing (e.g. a list of partner institutions goes in the Project's notes field as text, not as individual Organisation rows).
- `org-child-of` — a self-referential Link to Organisations (parent-organisation relationship), added since this schema knowledge was first written (confirmed via a fresh field-definitions export, Sept 2026). Not currently used by this skill's extraction logic — only add if the source material states a clear parent/subsidiary relationship, otherwise leave blank.
- `last-modified-by` / `last-modified-date` / `Created on` / `Created by` — Baserow system fields (read-only, the latter two confirmed via the same Sept 2026 review). Never write to these.

## Communities

`name-community` (formula), `description`, `name-community-long`, `name-community-abbreviation`, `people-leads`, `website`, `organisations`, `projects-sponsor`, `interactions`, `people-participants`, `last-modified-by`, `last-modified-date`

Notes:
- `name-community` is an **auto-computed formula column**, same pattern as `name-org`. Populate `name-community-long` (always) and `name-community-abbreviation` (only if given) instead.
- Can be added whenever mentioned, even if not the primary topic of the meeting.
- `people-leads` — Link to People, for leadership specifically. **As of a Sept 2026 schema review, Communities also has a direct general People-link field** — a People<->Communities relationship distinct from leadership. This reverses an earlier note in this file claiming no such field existed; that was correct when written but is no longer current. It was originally exported under a bare, incorrectly-generic name (`People`) and has since been corrected in Baserow to `people-participants` (confirmed via a re-export, Sept 2026) — update any reference to the old `People` spelling if you find one. **Note the naming collision**: this is a completely different field from the pre-existing `people-participants` field on the Interactions table (different table, different underlying field ID) — they happen to now share a name but track unrelated relationships; don't conflate the two when reading a candidates CSV or the output xlsx. A person's general contribution profile/competency areas still live on the People side, via `communities-contributor-profile`.
- `description` and `website` are genuine fields on this table now. There is **no `outputs`, `geographic-scope`, or `maturation-stage` field** — these were planned earlier but did not make it into the live structure. If notes describe any of these concepts, put them in `description` as free text rather than inventing a column.
- `organisations` — Link to Organisations (a Community can link to more than one).
- `projects-sponsor` / `interactions` — Link fields (Projects / Interactions). Note: this field was previously named `interactions-sponsor`; as of the same Sept 2026 review it's a plain `interactions` field on this table (no separate sponsor/funder distinction here, unlike Organisations' `interactions-sponsor`/`interactions-funder` pair, which is unchanged).
- Node-reconciliation: don't create an Organisations row AND a Communities row for the same name unless there's a real, fillable relationship-shape in both. If in doubt, only create the Organisations row and flag the possible Community angle for Cass.

## Projects

`name-project` (formula), `description`, `date-start`, `date-end`, `status`, `interactions`, `people-contacts`, `name-project-long`, `name-project-abbreviation`, `people-leads`, `people-contributors`, `github-issue`, `notes`, `org-sponsor`, `org-funder`, `communities`, `website`, `last-modified-by`, `last-modified-date`

Notes:
- `name-project` is an **auto-computed formula column**, same pattern as `name-org`. Populate `name-project-long` (always) and `name-project-abbreviation` (only if given) instead.
- `status` (single select). **Exact picklist for Projects specifically — NOT the same list as Interactions' status, see below:** `planned`, `ongoing`, `completed`, `paused`. Only four options here — there is no `pre-submission`/`submitted`/`rejected` on Projects' status field (that finer-grained bid/proposal lifecycle now lives on Interactions instead).
- `org-sponsor` / `org-funder` — two distinct Link-to-Organisations fields. If the notes don't clearly distinguish sponsor vs funder, flag rather than guessing.
- `communities` — Link to Communities (plural — a Project can link to more than one).
- `interactions` — Link to Interactions.
- `people-contacts` / `people-leads` / `people-contributors` — Link to People, three distinct roles.
- `github-issue` — URL to the corresponding issue in the team repo, only if the notes give one directly. Otherwise flag.
- Only add the **primary** project(s) actually under discussion.
- `last-modified-by` / `last-modified-date` — Baserow system fields (read-only). Never write to these.

## Interactions

`name-interaction` (formula), `status`, `date-started`, `notes`, `people-leads`, `projects`, `people-participants`, `name-interaction-long`, `name-interaction-abbreviation`, `type`, `urls-outputs`, `urls-internal`, `date-delivered`, `date-last-activity`, `github-issue`, `communities`, `org-sponsor`, `org-funder`, `last-modified-date`, `last-modified-by`, `Created on`, `Created by`

Notes:
- `name-interaction` is an **auto-computed formula column**, same pattern as `name-org`. Populate `name-interaction-long` (always) and `name-interaction-abbreviation` (only if given) instead.
- `status` (single select). **Exact picklist for Interactions specifically — NOT the same list as Projects' status:** `pre-submission / planned`, `submitted / under-review`, `active / confirmed`, `completed`, `rejected`, `paused`. Note the different wording from Projects — copy the exact strings including the ` / ` slash-separated phrasing.
- `type` (single select). Confirmed options (corrected against a fresh field-definitions export, Sept 2026 — this list previously documented `slack-only`, which has never been a real option; the live field is `slack-channel`, and it also gained `conference` and `seminar` since this schema knowledge was first written): `meeting`, `call-series`, `presentation`, `email-only`, `slack-channel`, `conference`, `seminar`. If a project/relationship already has a live meeting cadence (`meeting` or `call-series`), don't create a separate email/slack interaction row for it — summarise that activity in `notes` instead.
- **One Interactions row per notes file, not per dated meeting section within it, and not based on a guessed counterpart name.** A file is about one topic (often a project) — even if that topic's meetings span several dates with different attendees each time (e.g. someone joining for just one instalment), all of it belongs to the same single Interaction row. Name the interaction after the file's overall subject (e.g. the project or topic the whole file is about), not after any one date's specific attendees or a per-date guess. `people-leads`/`people-participants` should be the union of everyone who attended across all dated sections in the file, not just whoever was at the most recent one. This skill has no access to the live CRM, so it can't check whether a row for this exact topic already exists from a previous extraction run — just produce one candidate row per file per extraction run, and note in `notes` which meeting dates this run covers.
- `urls-outputs` / `urls-internal` — these are plain **Text** fields, not Baserow's URL field type, likely because a single interaction may need to reference more than one URL (a URL-type field can only hold one). Free text, potentially multiple URLs — don't assume single-value formatting.
- `org-sponsor` / `org-funder` — two distinct Link-to-Organisations fields, same sponsor/funder distinction as Projects.
- `communities` — Link to Communities.
- `date-started`: earliest meeting date across all dated sections in the file (only set once, when the row is first created).
- `date-last-activity`: most recent meeting date across all dated sections in the file — update this even when updating an otherwise-existing row.
- `date-delivered`: only set if the notes clearly indicate the engagement has concluded. Otherwise flag/leave blank.
- `last-modified-by` / `last-modified-date` / `Created on` / `Created by` — Baserow system fields (read-only, the latter two confirmed via a fresh field-definitions export, Sept 2026). Never write to these.

## Cross-cutting conventions

- **Scope**: only interactions run by RCM Cooperative's own community are recorded — not interactions run by other/external organisations that Cass merely attended or heard about.
- **Flagging**: any fact you couldn't determine directly from the notes should simply not be written as a line in the candidates CSV — an omitted field is automatically flagged in the output. See SKILL.md Step 4 for the exact hand-off mechanism.
- **No inference beyond the text.** Don't infer an organisation's legal form, a person's affiliation, or a project's status from general knowledge — only from what the notes state. If it takes outside knowledge to fill a value, leave it out instead.
- **Formula and system columns — never write to these directly, on any table:**
  - Formula (auto-computed display names): `name-person` (People), `name-org` (Organisations), `name-community` (Communities), `name-project` (Projects), `name-interaction` (Interactions).
  - System/read-only (auto-tracked by Baserow): `Last modified` / `Last modified by` (People), `last-modified-by` / `last-modified-date` (all other four tables).
- **Sponsor vs Funder** is a genuinely new distinction on this platform, appearing on Organisations↔Projects and Organisations↔Interactions. If the notes describe a financial/funding relationship without making clear whether it's sponsorship or funding specifically, flag it rather than picking one.
